# Проект
Сейчас ты будешь работать над проектом Checkie Lite, это Android-приложение, 
предназначенное для составления персональной базы отзывов о различных продуктах и услугах. 
Например, ты пошёл в ресторан, заказал себе блюдо и затем занёс его в Checkie, 
чтобы при следующем посещении вспомнить, что тебе понравилось, а что не понравилось.

Отзыв содержит в себе название продукта, бренд, фото, теги для поиска, текст комментария, 
текст достоинств, текст недостатков, оценку от 0 до 10. 
В текущей реализации продукт и отзыв на него это одна сущность.

Основные экраны:
- Главная (список всех отзывов) — MainContentScreen
- Создание/Редактирование отзыва — ReviewCreationContentScreen
- Детали отзыва — ReviewDetailsContentScreen
- Настройки — SettingsContentScreen
- Поиск — SearchContentScreen

Приложение полностью локальное и хранит все данные в базе данных, 
без синхронизации с сетью и доступом к интернету. 
Изменения в данных на всех экранах отображаются мгновенно, так как используется подписка на БД.

# Стек
Android, Kotlin, Jetpack Compose, Kotlin Coroutines, Room, TEA (The Elm Architecture), 
Clean Architecture, Api-Impl Modularization, Decompose, Koin

# Структура проекта
Все модули разделены на основные типы:
- core — корневой функционал приложения, переиспользуемый между другими модулями.
- common — тоже корневой функционал, но не имеющий прямого отношения конкретно к Checkie 
  и может быть переиспользован as is в других проектах.
- feature — функциональный модуль, содержащий в себе UI, логику презентации и опционально доменную логику.

Также большинство модулей разделены на Api-Impl. Для feature-модулей это обязательное правило. 
Для core-модулей, подразумевающих возможность нескольких вариантов реализации, 
используется Api-ImplName (например, navigation реализованный на decompose 
будет иметь название `decompose` для impl модуля).

Фактические модули проекта включают:
- `app`
- `common:android`
- `common:navigation:api:core`
- `common:navigation:api:ui`
- `common:navigation:decompose`
- `common:pure`
- `common:tea:android`
- `common:tea:compose`
- `common:tea:core`
- `common:ui`
- `common:update:{api,rustore}`
- `feature:gallery:{api,impl}`
- `feature:main:{api,impl}`
- `feature:review-creation:{api,impl}`
- `feature:review-details:{api,impl}`
- `feature:search:{api,impl}`
- `feature:settings:{api,impl}`
- `core:datasource:local:{api,impl}`
- `core:entity`
- `core:theme:{api,impl}`

# Границы ответственности модулей
- `common` должен оставаться максимально независимым от домена Checkie. 
  Если код можно вынести и переиспользовать в другом проекте без изменений, он должен жить в `common`.
- `core` содержит общеапповую доменную и инфраструктурную логику Checkie, 
  переиспользуемую между feature-модулями.
- `feature` содержит конкретный пользовательский сценарий или экранный поток.
- `app` только собирает приложение, DI, root navigation и Android entry points. 
  Бизнес-логика в `app` не должна появляться.

# Правила зависимостей
- `api` модуль не может зависеть от своего `impl`.
- Взаимодействие между feature-модулями должно идти через `feature:*:api`, а не через `feature:*:impl`.
- `feature:*:impl` может зависеть от `feature:*:api`, `core:*`, `common:*`, но не от чужих `feature:*:impl`.
- `common` не должен зависеть от `feature` и по возможности не должен зависеть от `core`.
- `domain` не должен зависеть от `presentation`.
- `presentation` не должен работать с Room, DAO, file I/O и другими инфраструктурными деталями напрямую.
- Доступ к данным должен идти через repository/use-case/абстракции слоя данных, а не через прямой вызов datasource из UI.

# Правила наименования пакетов
1. com.perfomer.checkielite — обязательный префикс
2. feature/core/common — уровень модуля
3. [featurename] — название модуля без пробелов и без underscore
4. data/domain/presentation — слой чистой архитектуры, располагать что-либо ВНЕ этих пакетов запрещено. Исключение  — DI модуль.
5. Допустимы дополнительные технические подпакеты внутри слоя, если они уточняют структуру, а не ломают её. Например: `presentation.screen.*`, `presentation.navigation`, `presentation.util`, `data.repository`, `data.datasource`, `data.mapper`.

Далее применимо для feature presentation:
- navigation — содержит Destination, это "точки входа" в экраны с параметрами или без
- screen — содержит пакеты с экранами этого модуля
    - [screenname] — содержит пакеты презентации экрана
        - tea — содержит логику презентации (TEA), Reducer, Store
            - core — содержит корневые сущности TEA для этого экрана (State, Event, Command, Effect)
            - actor — содержит Actor'ы этого экрана, в них выполняются внешние запросы от экрана (например, поход в БД)
        - ui — содержит вёрстку и связку с TEA
            - state — содержит UiState и UiStateMapper
            - widget — содержит Jetpack Compose виджеты
            - page — опциональный дополнительный уровень для крупных экранов, состоящих из нескольких логических частей
- util — утилиты, экстеншены и прочие общие вещи

Дополнительные правила наименования пакетов:
1. Запрещено использовать пробелы, _ и заглавные буквы. В приоритете выбирать короткие названия, но если это неуместно, то слеплять два слова в одно (например — reviewdetails)
2. Запрещено использовать множественное число (entities — неправильно, entity — правильно).

# Правила именования классов
- `*Screen` — composable с основной разметкой экрана без лишней инфраструктурной логики.
- `*ContentScreen` — entry composable экрана.
- `*Destination` — navigation entry point.
- `*Store`, `*Reducer`, `*State`, `*Event`, `*Command`, `*Effect` — сущности TEA.
- `*Actor` — обработчик внешних действий, IO, навигации, работы с репозиториями и другими side effects.
- `*UiState` и `*UiStateMapper` — отдельный слой преобразования presentation state в состояние для UI.
- `*Repository` / `*RepositoryImpl` — контракт и реализация доступа к данным.
- `*Di` — только DI-конфигурация модуля, без бизнес-логики.

# Правила TEA
- `Reducer` должен быть чистым: без IO, без доступа к БД, файловой системе, навигации и Android framework.
- `Actor` выполняет внешние действия и возвращает результат обратно в TEA-цикл.
- Одноразовые события не должны храниться в `State`. Для этого используй `Effect`.
- Навигация, тосты, открытие пикеров, запросы permissions и прочие одноразовые действия должны идти через `Effect`/navigation actor, а не через флаги, которые навсегда остаются в `State`.
- Если логика является чистым преобразованием данных, она должна жить в reducer/mapper/util, а не в actor.
- Если логика делает внешний вызов, она должна жить в actor, а не в reducer и не в composable.

# Правила Compose
- Composable-функции должны быть по возможности stateless и получать уже подготовленные данные.
- `Screen` отвечает за подключение к store, lifecycle, navigation, обработку effect.
- `ContentScreen` отвечает за layout и composition UI.
- `widget` не должен знать про repository, datasource, Room, DI и прочую инфраструктуру.
- Не размещай бизнес-логику и работу с данными внутри composable body.
- Тяжёлые вычисления и повторные преобразования в Compose должны быть либо заранее подготовлены, либо обёрнуты в `remember`/`derivedStateOf`, если это действительно нужно.
- Не вызывай side effects напрямую во время composition. Используй подходящие Compose effect APIs.

# Правила слоя данных и БД
- Любое изменение схемы Room должно сопровождаться миграцией, если это не осознанный breaking change.
- При изменении схемы БД необходимо обновлять schema snapshots.
- Изменения в модели хранения нужно оценивать с точки зрения совместимости backup/import/export.
- Код, работающий с файлами, Room, preferences и сериализацией, должен жить в `data`, а не в `presentation`.
- Маппинг между database/entity/domain/ui моделями должен быть явным и предсказуемым.

# Правила тестирования
- Изменения в `Reducer`, validator, mapper и другой чистой логике должны сопровождаться unit-тестами.
- Изменения в Room migration должны сопровождаться тестами миграций, если инфраструктура тестов в модуле это позволяет.
- При исправлении бага по возможности добавляй regression test на сценарий, который был сломан.
- Если тест не добавлен, причина должна быть понятной и технически обоснованной.

# Правила внесения изменений
- Перед добавлением нового класса или пакета сначала проверь, нет ли уже такого паттерна в соседнем feature или core/common модуле.
- Предпочитай встраиваться в существующий паттерн проекта, а не изобретать новый.
- Если правило из этого файла конфликтует с уже устоявшимся кодом в конкретном модуле, ориентируйся на локальный паттерн модуля и явно отмечай конфликт в отчёте.
- Не перемещай массово пакеты, не переименовывай префиксы и не делай архитектурный рефакторинг без явного запроса.

# Definition of Done
Перед завершением задачи проверь:
- код лежит в корректном модуле и пакете;
- архитектурные границы не нарушены;
- новый UI использует существующие паттерны TEA и Compose;
- новые строки вынесены в ресурсы, если это пользовательский текст;
- при изменении БД добавлены migration и schema update;
- выполнены релевантные проверки: как минимум сборка или тесты затронутого модуля, если это возможно в рамках задачи.

# Запрещено
- Ходить в БД, datasource или repository напрямую из composable.
- Помещать IO в reducer.
- Хранить одноразовые события в `State`, если для них нужен `Effect`.
- Добавлять зависимость на чужой `feature:*:impl`.
- Дублировать бизнес-логику в нескольких feature, если её можно вынести в `core`.
- Класть произвольную бизнес-логику в `app`.
